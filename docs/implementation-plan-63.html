一、最可能调整的决策（请先审阅）

以下不是“机械实现细节”。每项都给出推荐方案；用户若否决，后续 plan 应先按反馈改写。

待确认 D1PostHub-owned run/history 层与 publish_record 归属

问题：#73 的草案引用 account(id)，但 ADR-0006 已废弃 PostHub 自有 account/task/platform_job 表；当前账号真源是官方 user_info。同时，#76/#77 要求真实逐项结果、轮询、重试和中断恢复，这已经超出“只调用官方 HTTP”的旧边界。

推荐：先显式批准一个“只负责受理后观察/历史/人工重试”的 PostHub-owned 层；其数据放独立 posthub.db，与官方 database.db 并置，绝不跨库 FK。官方库继续只承载 user_info/file_records。

理由：避免上游初始化/升级重建官方库时丢历史；不把本地 run 状态伪装成 social-auto-upload 官方能力；仍可让单 worker 只编排批量执行，不恢复旧的通用调度器。

posthub.db
  batch_run / batch_item       -- #76/#77 运行观察与人工重试
  publish_record               -- 日历与跨提交软警示

publish_record(
  account_id INTEGER,            -- user_info.id 的历史观察值，不加 FK
  account_file TEXT NOT NULL,   -- cookie 文件名快照
  account_name TEXT NOT NULL,   -- 名称快照
  platform TEXT NOT NULL,       -- PostHub 字符串枚举
  run_id TEXT, run_item_id TEXT,
  video_id TEXT NOT NULL, video_title TEXT NOT NULL,
  scheduled_for TEXT NOT NULL,
  status TEXT NOT NULL
)

若不批准：只能记录提交 accepted/rejected，不能声称真实逐项 success/failure、轮询、interrupted 或发布日历事实；本路线的 #76/#77 目标需收缩。

待确认 D2原始 payload 与有效 payload 是否双存

问题：#76 只写了原始单项 payload；但账号默认声明、单账号拆分和平台时间降级都发生在受理边界。若重试时重新 merge，用户后来修改账号设置会改变原意。

推荐：在 batch_item 同时保存 submitted_payload_json（原始审计输入）与 effective_payload_json（受理时已校验、按账号拆分、已合并声明、可回放）。retry 只使用 effective 快照；parent_run_id 保留重试链。

理由：同时满足 #76 的审计语义与可靠重试语义；不会把“没填字段”误当成“重试时重新取默认”。若必须保持单列，则把 payload_json 明确定义为 effective，而不是含糊地称为 raw。

待确认 D3时间与时区边界

推荐：dailyTimes 单一升级为 string[]（"HH:MM"）；wrapper 根据当前机器本地时间计算绝对 naive datetime；本轮不增加 timezone/DST UI。

平台精度：抖音/小红书初始 minute；视频号/快手初始 hour，按注册表 round 到最近整点，并在预览与结果中显示实际提交时刻。

理由：沿用上游当前本地时钟语义，避免引入用户无法验证的时区转换；#66 已确认 HTTP seam 没有 timezone 字段。部署说明明确“以运行机器本地时间为准”，DST 留作后续需求。

若 PostHub 需要跨地区运行，D3 必须改为显式 IANA timezone + DST 规则，本 plan 不能直接落地。

待确认 D4“定时”页的日历入口

推荐：保留现有“定时”导航，在 ScheduleView 中采用“两段式”：上方为 #73 Variant B 全账号周总览，下方保留现有默认定时配置。

交互：默认本周；前后翻周与“本周”；今日列高亮；每行=账号名 + PlatformMark；单元格展示 HH:MM + 视频标题，scheduled 蓝色、published 绿色。

理由：不新增导航项、不丢现有配置；周总览能直接发现跨账号空档与撞档，符合用户已拍板的 Variant B。

待确认 D5内部声明队列的 canonical shape

问题：当前 select_for_platform() 返回扁平字段，但 uploader_wrapper.py 的注释/读取方式部分按嵌套字段理解；现有形状不一致，跨线程后更容易串台或丢声明。

推荐：收敛为一条内部契约：{ platform: type, fields: {...} }。fields 是已映射的上游中文字段；worker 每个 item 执行前 set，执行后 clear。
{ platform: 2, fields: { declaration: "无需标注" } }
{ platform: 1, fields: { source: "笔记含AI合成内容" } }

理由：外部 HTTP 仍使用 platformFields；内部只保留一个形状，避免当前扁平/嵌套混用。origin 依 #78 不在本路线图实现。

待确认 D6retry API 的选择粒度

推荐：POST /batchRuns/:id/retry 接收可选 { itemIds?: string[] }；省略时重试该 run 全部 failure/skipped/interrupted，指定时只重试指定的可重试项。

硬规则：success 永远不复制；pending/running 不可由用户重试；新 run 保存 parentRunId。

理由：同时支持 prototype B 的“逐项重试”和“重试全部”，不需要两个相互漂移的 endpoint。

待确认 D7单 worker 与既有跨平台并行语义

问题：项目总览/旧 ADR 曾写“跨平台并行 2–3”，但 #76 的可靠性方案锁定单 worker + Queue。

推荐：首版接受批量 item 全局串行，优先保证 per-item 隔离、浏览器资源安全、可恢复；同步更新 CONTEXT/ADR，明确这是 batch runner 的保守执行策略，不是恢复旧通用调度器。

理由：若保留跨平台并行，需要账号级锁、多个事件循环、退出/超时协调，明显扩大本轮风险；后续可单独压测后再拆并行度。

4.2 HTTP seam 与 PostHub-owned history API

边界：官方 /postVideo、/postVideoBatch 仍是发布能力 seam；/batchRuns、/publishRecords 是获批准后由 PostHub-owned 本机 history/runner 层提供的扩展，必须在 ADR/接口文档中单独标注，不能伪装为上游官方能力。

方法请求成功失败语义
POST /postVideoBatch现有对象数组；外部字段命名继续用 camelCase。200 { code: 200, data: { runId } }，含义是“已受理”。声明/结构预检失败：400、无 run、无发布副作用；已有 run：409 data.runId。
GET /batchRuns/:id路径参数 runId。run 概要 + 全量 items；一次查询聚合，按 seq 排序。404 明确提示 run 不存在。
GET /batchRuns?limit=5可选 limit。最近 run 概要，不含 items；供“最近运行”入口。不把 localStorage 当事实来源。
POST /batchRuns/:id/retry可选 { itemIds }。新 runId；只复制允许重试的 item。success 不可复制；单飞行冲突仍为 409。
GET /publishRecords?from=&to=本地日期范围。日历与提交前跨提交软警示共用记录查询。查询失败保留已有 UI 状态并提示，不把未知当无记录。

现有 parseOfficialResponse 只抛普通 Error；需增加保留 HTTP status/code/data 的 OfficialApiError，否则前端无法可靠识别 409 并打开已有 run。

4.3 声明三态

  • 继承账号默认：字段不写入任务 payload；后端受理时读取默认。
  • 明确无声明：视频号使用 wechat.declaration = "no_label"，抖音使用 douyin.declaration = "no_need"。
  • 具体声明：按 ADR-0008 的平台分键与英文枚举持久化，再由 wrapper 映射为中文文案。
  • 小红书：不新增“无声明”候选；上游无 source 路径时由 PostHub DOM wrapper 尝试注入，失败 warn 后继续。
  • origin：依 #78 明确不纳入本路线图验收和新实现。

自动化门

  • 异常隔离：第 2 item 抛错时第 1/3 item 仍完成；success item 不进入 retry payload。

真实平台手测（不进 CI）

组别步骤通过标准
定时 P0四平台分别提交明日、+3 天、候选窗口边界；混合 immediate/timer。定时项不立即发布；平台后台出现正确预约；错误项不影响其他项。
分钟抖音/小红书提交 HH:01/HH:30/HH:59；视频号检查 hour 降级；快手单独实测。支持分钟的平台保持分钟；hour 平台按最近整点提交，预览/结果所见即所发。
窗口now+1h、now+2h、候选 max−1/max/max+1。UI 只软提示；当前 enforcement=warn，平台实际拒绝记 failure，其他 item 继续；skipped 仅保留为未来 block 语义。
声明视频号 no_label/ai_generated；小红书 ai_synthesized；未填写。后台终值与所选枚举一致；DOM 缺失时有 warning/screenshot 且流程不假装成功。
run/幂等3 个素材 × 2 平台账号，故意制造一个无效 cookie；断开轮询；重启 daemon；再重试。页面显示受理、逐项结果、协议状态 completed_with_failures（UI 可标“部分成功”）；网络断开不误标失败；重启为 interrupted；只重试失败项。
409/查重一个 run 执行中再次提交；同批重复；跨提交已有成功记录。409 明确“本次未受理”；同批硬阻断；跨提交仅警示且二次确认。
日历核对 scheduled/published 记录、跨周、删除账号后历史。周总览与实际受理时间一致；删除账号不抹历史快照。

七、明确不做与风险缓释

不做

  • 不 fork、不改 social-auto-upload；所有扩展留在 PostHub wrapper 与明确标注的本机 history/runner 层。
  • 不恢复自研通用规则排期、平台回查、自动分阶段补提、hash+日期自动去重；仅在 D1 批准后做批量受理后的观察/人工重试编排。
  • 不处理 origin 声明原创开关；现有 picker 控件属于既有能力，不在本路线图扩大或宣称可靠。
  • 不把 localStorage 完整结果当数据库；不自动续跑 interrupted run。
  • 不在本轮引入 timezone/DST 产品模型；机器本地时间限制必须写入文档。

主要风险

  • 上游签名漂移：导入期签名守卫 + 四平台 wrapper 单测，启动即报清晰错误。
  • DOM 漂移：双 selector、warning、debug screenshot；真实账号验收回填 selector。
  • 线程/浏览器资源：单 worker、单飞行、item 超时；若同步阻塞导致 worker 卡死，升级路径再考虑独立子进程。
  • 平台窗口不确定：只做候选值 warn；真实复测后另开 ticket 决定是否收紧。
  • 数据模型漂移：D1 先确认；禁止直接照抄 #73 的旧 account FK。
